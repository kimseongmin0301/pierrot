## 1. 배경: 왜 이 주제인가

### 1-1. 목표 직무

AI / AX 엔지니어. 이 직무에서 주로 보는 역량은 세 가지입니다.

1. **LLM을 실제 업무 흐름에 붙이는 능력**: RAG, 에이전트, 도구 호출(Tool Calling)
2. **AI 결과를 믿을 수 있게 만드는 능력**: 평가(Evaluation), 가드레일, 환각 탐지
3. **운영 능력**: 로그, 모니터링, 비용과 지연시간 관리

RAG 챗봇과 에이전트는 이미 구축 경험이 있으므로, 이 프로젝트는 **2번(신뢰성)**을 차별점으로 보여주는 데 집중합니다.

### 1-2. 삐에로라는 주제와의 연결

삐에로(Pierrot)는 이탈리아 즉흥극(코메디아 델라르테)에서 유래한 캐릭터로,
**웃는 분장 뒤에 슬픔을 숨긴 광대**라는 상징을 가집니다.

LLM도 틀린 답을 할 때 자신 있게 웃는 얼굴로 말합니다. 이것이 "LLM의 가면"입니다.
PIERROT는 이 가면을 벗겨서 답변의 실제 근거 여부를 드러내는 시스템입니다.

또한 "신뢰를 중요하게 여기고, 결과를 의심하고 직접 검증한다"는 개발자 본인의 강점이
프로젝트 주제와 일치하므로, 면접에서 일관된 이야기로 연결할 수 있습니다.

## 2. 동작 흐름 (금융 도메인 예시)

```
사용자 질문: "삼성전자 3분기 영업이익과 주가 흐름 요약해줘"
        ↓
[1] 답변 생성 LLM
    - 일반적인 RAG 방식으로 답변 생성
        ↓
[2] 주장 분해 (Claim Extraction)
    - 답변을 검증 가능한 최소 문장 단위로 분리
    - 예: "3분기 영업이익은 X조원이다"
          "발표 후 주가가 5% 상승했다"
        ↓
[3] 검증 에이전트
    - 주장의 유형을 분류하고, 유형에 맞는 도구를 선택해 확인
    - 숫자 주장  → DART 공시 API 조회
    - 주가 주장  → OHLCV 데이터 조회 후 직접 계산
    - 서술 주장  → 원문 문서와 의미 비교 (NLI 모델)
        ↓
[4] 판정
    - 주장별로 세 가지 중 하나로 판정
      · SUPPORTED     : 근거 있음
      · CONTRADICTED  : 근거와 모순
      · UNVERIFIABLE  : 근거를 찾을 수 없음
        ↓
[5] 최종 출력
    - 원래 답변에 주장별 신뢰 표시를 붙임
    - CONTRADICTED 주장은 근거와 함께 수정 제안
```

## 5. 평가 설계 (이 프로젝트의 핵심)

포트폴리오가 "만들어 봤다"로 끝나지 않으려면 **검증기 자체를 검증해야** 합니다.

1. **테스트셋 구축** (2026-11-18 구현, `evaluation/testset.py`)

   초안은 "정상 답변에 오류를 섞는다"였는데, 실제로 만들어 보니 **답변이 아니라
   주장 단위로 생성하는 것이 맞았습니다.** 답변을 만들면 그 안의 주장마다 다시
   사람이 라벨을 붙여야 하고, 붙인 라벨이 맞는지 또 검증해야 합니다.

   대신 **이미 검증된 스냅샷에서 주장을 직접 생성합니다.**
   DART와 거래소에서 받은 값이라 근거가 확실하고, 값을 일부러 틀리게 바꾸면
   그 주장은 반드시 거짓입니다. **라벨이 생성 규칙에서 나오므로 의심할 여지가 없습니다.**

   | 라벨 | 생성 방식 | 개수 |
   |---|---|---|
   | SUPPORTED | 스냅샷 값을 그대로 옮김 | 100 |
   | CONTRADICTED | 금액 30%/15% 변형, 증감 방향 뒤집기 | 100 |
   | UNVERIFIABLE | 스냅샷에 없는 연도(2019년) | 100 |

   유형은 NUMERIC 150 / PRICE 150. seed를 고정해 다시 돌려도 같은 셋이 나옵니다.
   지표를 비교하려면 테스트셋이 고정되어야 하기 때문입니다.

   **이 방식의 한계**: 문장 틀이 정해져 있어 실제 LLM 환각과 분포가 다릅니다.
   그래서 1단계에서 `gemma3:4b`가 실제로 만든 주장 91개를 보조 세트로 둡니다.
   다만 정답 라벨이 없으므로 지표 계산에는 쓰지 않고, "실제 환각에서도 같은
   경향이 나오는가"를 보는 용도입니다.

2. **측정 지표** (`evaluation/metrics.py`, 외부 의존성 없음)
   - 재현율(Recall): 틀린 주장을 얼마나 잡아내는가
   - 오탐률(False Positive Rate): 맞는 주장을 틀렸다고 잘못 판정하는 비율
   - 정밀도(Precision): CONTRADICTED로 판정한 것 중 실제로 틀린 비율
   - **커버리지**: 판정이 필요한 주장 중 실제로 판정한 비율 (추가)

   커버리지를 넣은 이유: UNVERIFIABLE을 맞고 틀림으로 나누면 지표가 왜곡됩니다.
   **전부 보류하는 검증기는 오탐률 0%로 가장 좋아 보입니다.** 커버리지가 0%로
   드러나야 그것이 쓸모없다는 것이 보입니다. 테스트로 고정해 뒀습니다
   (`test_abstain_everything_verifier`).

   이 모듈은 표준 라이브러리만 씁니다. 결론을 만드는 숫자가 LangChain이나
   pandas 버전에 따라 달라지면 몇 달 뒤 같은 결과를 못 뽑기 때문입니다(7-2 원칙).

3. **비교 실험 결과** (2026-11-18 실측, `evaluation/run_eval.py`)

   세 방법에 **같은 테스트셋, 같은 근거**를 줬습니다. 한쪽에만 불리한 조건을 주면
   "도구가 낫다"는 결론이 조작이 됩니다.

   | | 쉬운 셋 (300건) | | | 어려운 셋 (200건) | | |
   |---|---|---|---|---|---|---|
   | | 재현율 | 오탐률 | 커버리지 | 재현율 | 오탐률 | 커버리지 |
   | **도구 기반** | **100%** | **0%** | **100%** | **100%** | **0%** | **100%** |
   | NLI 베이스라인 | 61.0% | 34.0% | 60.0% | 15.4% | 45.3% | 66.0% |
   | LLM-as-judge | 53.0% | 6.0% | 51.5% | 46.2% | 31.1% | 67.5% |

   쉬운 셋은 스냅샷 값을 포맷터 표기 그대로 옮긴 주장,
   어려운 셋은 실제 LLM이 말하는 방식(어림수, 억 단위, 소수 표기, 모호한 날짜,
   기준 미표기)으로 만든 주장입니다.

   **어려운 셋에서 격차가 벌어집니다.** NLI는 재현율 61% → 15.4%로 무너지고,
   LLM-as-judge는 정밀도가 89.8% → 34.3%로 떨어집니다. 도구는 유지합니다.

   주장 유형별로 보면 원인이 분명합니다.

   | 재현율 | NUMERIC | PRICE |
   |---|---|---|
   | 도구 기반 | 100% | **100%** |
   | NLI 베이스라인 | 33.3% | **10.0%** |
   | LLM-as-judge | 91.7% | **32.5%** |

   LLM-as-judge는 어림수 과장 판단(`rounded_overstated`)을 91.7%로 잘합니다.
   하지만 "2024년 6월 중순" 같은 모호한 날짜의 주가는 32.5%입니다.
   **근거 문장에 그 날짜가 적혀 있지 않으면 판정할 수 없습니다.**
   도구는 임의 날짜를 조회해 계산합니다.

   NLI 실패는 2단계에서 `scripts/probe_nli_limits.py`로 **미리 측정해 둔
   실패 유형이 그대로 재현**된 것입니다.

   ```
   "2,589,355억원"  vs 근거 "258조 9,354억원"   → 모순 0.999  (같은 값, 다른 표기)
   "약 301조원"     vs 근거 "별도 209조 522억"  → 모순 0.992  (엉뚱한 근거 선택)
   ```

4. **이 100%를 어떻게 읽어야 하는가**

   테스트셋을 스냅샷에서 생성했으므로 **도구가 데이터를 반드시 보유한 조건**입니다.
   어려운 셋은 *표현*을 어렵게 만들었을 뿐 *데이터 가용성*은 보장했습니다.
   따라서 100%는 다음을 뜻합니다.

   > 데이터가 있는 주장에 대해, 표현이 다양해도 올바로 파싱하고 비교한다.

   실제 LLM 답변에 대한 성능은 **커버리지로 따로 재야 합니다.**
   1단계에서 `gemma3:4b`가 만든 주장 53건에 돌린 결과입니다.

   ```
   모순      30건 (56.6%)
   확인 불가  23건 (43.4%)   ← 재무제표 주요계정에 없음 16건
                              기간·시점 특정 불가 3건, 기타 4건
   커버리지 56.6%
   ```

   즉 **판정할 수 있는 주장은 정확히 판정하지만, 실제 답변의 43%는 도구가
   다루지 못하는 내용**(수주액, 배당금, 부문별 매출)입니다.
   이것이 다음에 붙일 도구를 정하는 기준이 됩니다.

5. **라벨 생성에서 찾은 오류**

   처음에는 연결 기준만 보고 라벨을 붙였는데, 도구는 연결과 별도를 둘 다 봅니다.
   그래서 별도 기준으로 맞는 주장을 "도구가 놓쳤다"고 잘못 세었습니다.

   ```
   "셀트리온의 2024년 매출액은 약 4조원이다"
     연결 3조 5,573억 (12.4% 차이) → CONTRADICTED 로 라벨
     별도 3조 7,092억 ( 7.8% 차이) → 도구는 별도와 일치로 판정
   ```

   기준을 밝히지 않은 주장이므로 별도와 맞으면 참입니다. 라벨 생성기를 고쳤고,
   수정 후 도구는 200/200이 되었습니다. **평가 코드의 버그가 지표를 왜곡할 수
   있다는 사례**이므로 기록해 둡니다.

4. **테스트셋의 한계를 명시합니다**
   - 오류 주입으로 만든 테스트셋은 정답 라벨이 정확한 대신, 실제 LLM이 내는 환각과
     분포가 다릅니다. 이 한계를 숨기지 않고 README에 명시합니다.
   - 가능하면 `generator`(`gemma3:4b`)가 실제로 만들어 낸 환각 샘플을 소수라도 수집해
     보조 검증 세트로 함께 사용합니다.

## 7. 확정된 결정 사항 (2026-11-18)

### 7-1. LLM 구성

| 자리 | 모델 | 실행 위치 | 비용 |
|---|---|---|---|
| `generator` (검증 대상 답변 생성) | `gemma3:4b` | ai-server (Ollama) | $0 |
| `generator` 비교 실험 (선택) | `qwen3:4b` | ai-server (Ollama) | $0 |
| RAG 임베딩 | `embeddinggemma` | ai-server (Ollama) | $0 |
| `extractor` (주장 분해) | `gpt-4o-mini` | OpenAI API | 유료 |
| `verifier` (검증 판단) | `gpt-4o-mini` | OpenAI API | 유료 |
| 베이스라인 ① NLI | `Huffon/klue-roberta-base-nli` | 로컬 CPU | $0 |
| 베이스라인 ② LLM-as-judge | `gpt-4o-mini` | OpenAI API | 유료 |

**선정 근거**

- `generator`는 검증 **대상**이므로 품질이 좋을 필요가 없고, 오히려 환각이 섞여야 시연이 자연스럽습니다.
  4B급 로컬 모델이 이 역할에 적합하며, "사내 로컬 LLM의 답변을 검증한다"는 서사는 외부 API 반출이
  어려운 금융권 환경과 그대로 맞아떨어집니다.
- `extractor` / `verifier`는 시스템의 **부품**이므로 품질이 중요합니다. `gpt-4o-mini`는 추론 모델이
  아니라 비용 예측이 정확하고, Structured Outputs(JSON 스키마 강제)를 지원해 파싱이 안정적이며,
  LangChain 자료가 가장 많습니다.
- 1단계 완료 기준(샘플 10개 사람 검토)에서 주장 분해 품질이 부족하면 그때 `gpt-5-mini`로 올립니다.

**예산: 월 $5**

| 항목 | 평가 1회 비용 |
|---|---|
| `generator` (로컬) | $0 |
| `extractor` | 약 $0.14 |
| `verifier` | 약 $0.50 |
| 베이스라인 ① NLI (로컬) | $0 |
| 베이스라인 ② LLM-as-judge | 약 $0.32 |
| **합계** | **약 $0.95** |

Batch API(50% 할인) 적용 시 약 $0.48. 월 $5로 전체 평가를 5~10회 실행 가능합니다.

**예산을 지키기 위한 필수 장치 (0단계에 포함)**

1. **디스크 응답 캐시** — 프롬프트 해시를 키로 응답을 저장. 재실행 시 변경된 부분만 과금됩니다.
   비용 절감과 동시에 평가 재현성을 확보하는 장치이기도 합니다.
2. **토큰·비용 로거** — 모든 호출의 입출력 토큰과 환산 비용을 기록합니다.
   원래 6단계 항목이었으나 **0단계로 앞당깁니다.** 예산이 $5면 사용량을 모르는 채로 개발할 수 없습니다.
3. **개발 중 미니 테스트셋** — 평소 개발은 10~20개 샘플로, 전체 300개는 로직 확정 후에만 실행합니다.

### 7-2. 에이전트 구현 방식 — LangChain + LangGraph

| 도구 | 담당 |
|---|---|
| LangChain | LLM 호출, 프롬프트 템플릿, 출력 파싱, SQLite 응답 캐시(`set_llm_cache`) |
| LangGraph | `verifier`의 상태 머신: 유형 분류 → 도구 선택 → 호출 → 실패 시 재시도 → 판정 |
| LangSmith | 요청별 트레이싱(선택, 무료 티어). 토큰·지연시간 기록을 자동화 |

**경계선**: `evaluation` 모듈은 LangChain에 의존시키지 않습니다. 지표 계산(정밀도/재현율/오탐률)은
순수 파이썬으로 유지합니다. 프레임워크 버전 변경으로 과거 평가 결과를 재현하지 못하는 상황을
막기 위해서입니다. 이 프로젝트의 핵심 주장이 "숫자로 증명했다"인 이상, 그 숫자를 만드는 코드는
외부 의존성이 가장 적어야 합니다.

### 7-3. 주가 데이터 소스 — FinanceDataReader

**원칙: 평가 실행 중에는 외부에서 주가를 조회하지 않습니다.**

```
[1회성 수집 스크립트]  →  로컬 스냅샷(parquet)  →  [검증 도구가 조회]
  FinanceDataReader 사용        저장소에 커밋          외부 접속 없음
```

pykrx, FinanceDataReader 등은 공식 API가 아니라 거래소·포털을 크롤링하는 비공식 라이브러리입니다.
대상 사이트 구조가 바뀌면 동작이 멈추고, 수정주가 반영 시점에 따라 값이 달라질 수 있습니다.
외부 의존성을 재현성 경계 밖으로 밀어내기 위해 스냅샷 방식을 사용합니다.

- 수집 범위(확정): 고정 유니버스 20종목, **2023-01-02 ~ 2026-11-18**
  (18,920행, 494KB, `data/snapshots/kospi_ohlcv.parquet`)
- **종목 유니버스를 코드에 고정합니다** (`src/pierrot/tools/universe.py`).
  "시가총액 상위 20종목"처럼 동적으로 정하면 돌리는 시점마다 구성이 바뀌어 평가를
  재현할 수 없습니다. 유니버스는 실험 조건의 일부이므로 고정하고 커밋으로 흔적을 남깁니다.
  구성은 1단계 샘플에 등장한 10개 기업 + 코스피 대형주 10개입니다.
  (참고: `fdr.StockListing('KOSPI')`의 시가총액 필드가 `NaN`이라 동적 선정이 불가능하기도 합니다.)
- 종목명↔종목코드 매핑은 유니버스에 별칭까지 적어 두고 직접 찾습니다.
  "현대자동차"나 "포스코홀딩스" 같은 표기도 이어져야 하기 때문입니다.
- 등락률은 LLM에게 묻지 않고 **파이썬으로 직접 계산**합니다. 이것이 도구 기반 검증의 핵심입니다.

#### 발견된 한계: 수정주가 (2026-11-18)

스냅샷을 받아 보니 20종목 중 3종목의 과거 시세가 **수정주가로 보정**되어 있었습니다.
분할·합병·인적분할이 있으면 과거 가격이 소급 조정되기 때문입니다.

| 종목 | 호가 단위에 맞는 종가 비율 |
|---|---|
| 삼성바이오로직스 | 3.6% |
| 셀트리온 | 12.8% |
| 삼성SDI | 41.6% |
| 나머지 17종목 | 99.9 ~ 100% |

**왜 문제인가**: LLM이 "2024년 7월 26일 주가는 85만원이었다"고 말할 때 그 값은
당시 호가를 가리킵니다. 보정된 시세(1,336,279원)와 비교하면 맞는 주장을 틀렸다고
판정하게 됩니다. 오탐은 이 프로젝트가 가장 피해야 할 오류입니다.

**반대로 등락률 주장에는 수정주가가 맞습니다.** 분할 전후를 비교 가능하게 만드는
것이 수정주가의 목적이기 때문입니다.

**대응**: 보정 여부를 호가 단위 검사로 **자동 탐지**하고(목록을 코드에 적지 않습니다.
스냅샷을 다시 받으면 대상이 달라지는데 하드코딩하면 조용히 틀린 채로 남습니다),
보정된 종목의 "얼마였다" 주장만 UNVERIFIABLE 로 둡니다. 등락률 주장은 그대로 판정합니다.

**해결 (2026-11-18 결정)**: KRX 정보데이터시스템(`data.krx.co.kr`)은 **무료 회원가입**
사이트이고, pykrx 의 `adjusted=False`(`adjStkPrc=1`, 단순종가)로 원주가를 받을 수
있습니다. 비로그인 API 접근이 막혀 있어 계정이 필요할 뿐입니다.

그래서 스냅샷에 **두 시리즈를 함께 저장**합니다.

| 컬럼 | 내용 | 쓰이는 곳 |
|---|---|---|
| `open/high/low/close` | 수정주가 (FinanceDataReader) | 등락률 주장 |
| `open_raw/high_raw/low_raw/close_raw` | 원주가 (KRX) | 값 주장("얼마였다") |

이렇게 하면 트레이드오프가 사라집니다. 값 주장은 당시 실제 호가와, 등락률 주장은
분할 보정된 시세와 비교하게 됩니다. 3종목을 포기할 필요가 없습니다.

**재현성은 그대로입니다.** KRX 로그인은 수집할 때만 필요하고, 검증은 저장된 스냅샷만
읽습니다. KRX 가 막히거나 pykrx 가 깨져도 커밋된 스냅샷으로 평가는 계속 돌아갑니다.

자격증명은 `.env` 의 `KRX_ID` / `KRX_PW` 에 둡니다(`.gitignore` 등록됨).
원주가 없이 진행하려면 `--skip-raw` 를 쓰고, 그 경우 보정된 종목의 값 주장만
UNVERIFIABLE 로 남습니다.

#### 발견된 한계 2: 일률 허용 오차는 환각을 놓칩니다 (2026-11-18)

처음에는 가격 주장에 일률 3% 허용 오차를 썼습니다. 그 결과
"2024년 4월 중순 POSCO홀딩스 주가는 36만원이었다"가 **근거 있음으로 통과**했습니다.

그 기간 실제 종가는 371,000 ~ 400,000원이고 장중 저가 최저도 371,000원이라
36만원은 한 번도 나온 적 없는 가격입니다. 3% 하한이 359,870원이어서
**130원 차이로** 통과한 것입니다. 환각을 놓친 것(미탐)입니다.

더 나쁜 것은, 이것이 18개 중 유일한 SUPPORTED 판정이었다는 점입니다.
즉 "허용 오차가 결과를 좌우하지 않는다"는 당시 판단이 틀렸습니다.

**해결**: 허용 오차를 주장에 적힌 **자릿수**에서 읽어 냅니다.

| 주장 표기 | 읽히는 단위 | 허용 오차 |
|---|---|---|
| 36만원 | 만원 | ±5,000원 → 365,000이 상한이라 371,000과 겹치지 않음 |
| 37만원 | 만원 | ±5,000원 → 375,000이 상한이라 371,000 포함, 인정 |
| 71,800원 | 백원 | ±359원 (하한 0.5% 적용) |
| 7만원 | 만원 | ±3,500원 (상한 5% 적용) |

정밀하게 말할수록 엄격하게, 어림수로 말할수록 너그럽게 봅니다.
관측값은 실제 데이터이므로 넓히지 않고, 어림수로 말한 **주장 쪽만** 넓힙니다.

하한(0.5%)과 상한(5%)을 두는 이유: 하한이 없으면 "71,800원"에 ±50원만 허용해
반올림 차이로도 모순이 나고, 상한이 없으면 "30만원"에 ±50,000원을 허용해
너무 관대해집니다.

### 2단계 착수 순서를 바꾼 이유 (NLI 먼저 → 주가 먼저)

계획 초안은 NLI를 먼저 만드는 것이었으나, 실제로는 NLI가 가장 복잡합니다.
혼자서는 아무것도 못 하기 때문입니다.

| 도구 | 근거를 어디서 가져오나 |
|---|---|
| 주가 | 스스로 해결. 로컬 스냅샷에서 조회 |
| DART | 스스로 해결. API가 수치를 직접 반환 |
| NLI | **해결 못 함.** 비교할 근거 문서가 어디에도 없음 |

`generator`는 환각을 유도하려고 RAG 없이 답변을 만들었으므로 참고 문서가 존재하지 않습니다.
NLI부터 만들면 "무엇과 비교할 것인가"가 공중에 뜬 채로 도구를 만들게 됩니다.
반면 DART 도구를 만들면 거기서 받아 오는 **공시 원문이 곧 NLI의 근거 문서**가 되므로,
주가 → DART → NLI 순서로 가면 각 단계가 다음 단계의 입력을 만들어 줍니다.

### 7-4. NLI 모델과 베이스라인 구성

**베이스라인을 2단으로 둡니다.**

| 단계 | 방식 | 역할 |
|---|---|---|
| 베이스라인 ① | `Huffon/klue-roberta-base-nli` | 전통적 방식. 숫자에 약하다는 것을 실측으로 보여주는 자리 |
| 베이스라인 ② | LLM-as-judge (`gpt-4o-mini`) | "요즘은 LLM에 직접 물어보면 되지 않나"라는 가장 현실적인 반론 |
| 개선안 | 도구 기반 검증 (DART, 주가 계산) | 이 프로젝트의 주장 |

베이스라인이 하나뿐이면 "NLI 모델을 약한 걸 골라 놓고 이긴 것 아닌가"라는 반론을 막을 수 없습니다.
②가 있어야 **"NLI보다 나은 건 당연하고, LLM에게 직접 물어보는 방식보다도 낫다"**는 결론이 가능합니다.

#### 정정: NLI는 숫자를 구분합니다 (2026-11-18 실측)

초안에는 **"NLI는 숫자를 값으로 보지 못해 9조원과 10조원을 함의로 판정한다"**고 적었습니다.
`Huffon/klue-roberta-base-nli`로 실제 측정해 보니 **틀렸습니다.**

```
전제: 삼성전자의 2024년 3분기 영업이익은 연결 기준 9조 1,833억원이다.
  "9조 1,833억원"  → ENTAILMENT    0.999
  "9조원"          → ENTAILMENT    0.999   (어림수, 맞음)
  "10조원"         → CONTRADICTION 0.999
  "5조원"          → CONTRADICTION 0.999
  "3,000억원"      → CONTRADICTION 0.998
```

추측으로 베이스라인의 한계를 적으면 "약한 상대를 만들어 이겼다"가 됩니다.
그래서 조건을 바꿔 가며 다시 측정했습니다(`scripts/probe_nli_limits.py`, 15개 중 10개 일치).

**실측으로 확인한 NLI의 진짜 약점**

| 약점 | 실측 사례 | 결과 |
|---|---|---|
| 표기가 다르면 같은 값도 모순 | `9조 1,833억원` vs `9.18조원` | CONTRADICTION 0.808 |
| 간단한 계산도 못 함 | `81,800→61,500` vs `20,300원 하락` | CONTRADICTION 0.996 |
| 근거에 없으면 판정 불가 | 다른 분기 수치 | NEUTRAL |
| 숫자 같으면 기준 차이 무시 | `별도 12조 3,610억` vs 기준 없는 동일 금액 | ENTAILMENT 0.999 |

즉 NLI는 **같은 표기로 미리 적어 둔 사실만** 판정할 수 있습니다.
표기를 정규화하거나(9조 1,800억원 = 9.18조원), 값을 계산하거나(등락률, 4분기 = 연간 − 1~3분기),
임의 조건으로 조회하는 일은 하지 못합니다. **이것이 도구가 필요한 진짜 이유입니다.**

#### 베이스라인 비교 결과 (2026-11-18, 주장 91개)

NLI에게도 DART·거래소에서 받은 검증된 사실을 근거로 줬습니다. 근거를 부실하게 주고
이기면 결론이 조작이 되기 때문입니다. 근거는 두 종류입니다.

- **수치 근거**: 스냅샷에서 기계적으로 만든 문장 (종목·연도당 약 50개)
- **공시 본문**: 사업보고서의 "사업의 내용"·"경영진단" 절에서 추출 (25,370문장)

근거 구성을 바꿔 가며 세 번 돌렸습니다.

| 설정 | NLI 모순 | NARRATIVE 확인불가 | 도구와 일치 | 비고 |
|---|---|---|---|---|
| 수치 근거만 | 20 | 31 / 38 | 69.8% | 서술 주장을 거의 못 다룸 |
| 수치 + 본문 **전체** | 41 | 7 / 38 | 64.2% | **거짓 모순 다수** |
| 수치 + 본문 **검색 top-30** | 23 | 26 / 38 | **71.7%** | 채택 |

**본문을 전부 넣으면 오히려 나빠집니다.** 주장 하나에 근거가 500개가 되고 그중
최댓값을 취하니, 관련 없는 문장에서 거짓 모순이 쏟아졌습니다.

```
주장: 2023년 현대차의 배당금 지급액은 4조 6천억 원이었다
판정 근거: "... 이자율스왑 160,000 - 808 파생상품부채 ..."  → 모순 0.995
```

실제 NLI 팩트체킹은 검색으로 추린 뒤 판정합니다. 전부에 돌려 최댓값을 쓰는 것은
표준적인 방식이 아니고, 공정하게 만들기는커녕 쓰레기를 만듭니다.

**최종 비교 (도구·NLI를 모두 돌린 주장 53개)**

```
                 도구    NLI
CONTRADICTED      30     23
UNVERIFIABLE      23     30
판정 일치  38/53 (71.7%)

도구는 잡았으나 NLI가 놓친 주장   11건
NLI만 모순으로 잡은 주장          4건
```

NLI가 놓친 11건은 대부분 **일별 주가 주장**입니다. 근거 문장이 연간·분기 단위라
"2024년 5월 8일 카카오 주가는 7만 9,100원"에는 비교할 문장이 아예 없습니다
(최대 함의 0.001). 도구는 임의 날짜를 조회합니다.

#### 남은 문제 (3단계에서 다룰 것)

1. **검색이 병목입니다.** 어휘 기반이라 의미가 같아도 표현이 다르면 못 찾습니다.
   ```
   주장: 삼성전자의 반도체 사업 부문 실적이 크게 개선되었다
   문서: DS 부문의 제56기 매출은 111조 660억원으로 66.8% 증가하였으며...
   → 겹치는 낱말 0 (반도체 vs DS, 개선 vs 증가)
   ```
   IDF 가중치를 넣어 "반도체" 문장이 5위까지 올라왔지만 여전히 "실적", "크게" 같은
   흔한 낱말에 밀립니다. 임베딩 검색(`embeddinggemma` 보유)이 다음 단계입니다.

2. **거짓 판정이 남아 있습니다.** NLI 모순 23건 중 일부는 무관한 문장에서 나왔습니다.
   ```
   "POSCO 주가 수익률 18%"   vs 수익성지표 표 조각   → 거짓 모순 0.999
   "삼성전자 주가 변동성"     vs 부채비율 문장       → 거짓 모순 0.949
   ```
   표 필터가 `(2) 수익성지표 구분 산식 ...` 형태를 아직 거르지 못합니다.

3. **정밀도·재현율을 아직 계산하지 않았습니다.** 지금은 도구와 NLI의 판정을
   비교했을 뿐, 정답 라벨이 없습니다. 4단계 테스트셋이 있어야 진짜 지표가 나옵니다.

## 7-7. 3단계 검증 에이전트 (2026-11-19 완료)

### 그래프 구조

```
주장 ─→ classify ─┬─ PRICE ─────→ price ────┐
                  ├─ NUMERIC ───→ numeric ──┼─→ (확인 불가면) ─→ narrative ─┐
                  ├─ NARRATIVE ─→ narrative ┘                               │
                  └─ FORECAST ──→ forecast ────────────────────────────────┴─→ finalize
```

구현: `src/pierrot/verifier/` (state / routing / tools / nodes / graph).
실행: `scripts/run_verifier.py`.

### 라우팅을 규칙으로 둔 이유

세 갈래 분류에 LLM 호출 비용을 치를 이유가 없습니다. 더 중요한 것은
**규칙은 테스트로 고정할 수 있지만 LLM 분류는 그렇지 않다**는 점입니다.
라우팅이 추출기 유형을 뒤집은 경우에는 사유를 결과에 남깁니다.

실측: 91건 중 **33건의 유형을 뒤집었습니다.** 추출기가 NARRATIVE 로 분류한
38건 중 28건이 실제로는 수치 주장이거나 전망이었습니다.

| 유형 | 추출기 | 에이전트 |
|---|---|---|
| PRICE | 18 | 24 |
| NUMERIC | 35 | 42 |
| NARRATIVE | 38 | 10 |
| FORECAST | 0 | 15 |

이 재분류로 **모순 적발이 30건에서 36건으로 늘었습니다.**
늘어난 건들은 전부 기존 스크립트가 아예 도구에 넣지 않던 주장입니다.

### 전망·권고 주장은 흘려보냅니다

거르지 않고 `FORECAST` 경로로 보내 UNVERIFIABLE + 사유를 남깁니다.
걸러 버리면 분모에서 사라져 지표가 좋아 보이지만, 그것은 성능이 아니라
측정 대상을 줄인 것입니다. 대신 커버리지를 두 갈래로 냅니다.

1단계 품질 휴리스틱(`quality.looks_like_forecast`)이 놓치던 네 형태
("~로 예상된다", "예상 OO은", "~할 계획이다", "~넘어설 것이다")를
`verifier/routing.py` 에 보강했습니다. `quality.py` 는 1단계 측정 수치에
묶여 있어 건드리지 않았습니다.

**확인한 것**: 전망 규칙을 넓히면 이미 잡아내던 모순을 삼킬 위험이 있습니다.
기존 CONTRADICTED 30건 중 FORECAST 로 새는 것은 **0건**입니다(회귀 테스트로 고정).

### 실측 결과 (주장 91건, 대체 경로 끔)

| 항목 | 값 |
|---|---|
| 모순 | 36건 |
| 확인 불가 | 55건 (전망 15 + 데이터 없음 40) |
| 커버리지 (전체) | 39.6% |
| 커버리지 (전망 제외) | 47.4% |
| 커버리지 (계산 기반만) | 37.4% |
| 처리 속도 | 0.54초/주장 |

### 판정의 성격을 구분합니다 (`Confidence`)

같은 CONTRADICTED 라도 근거의 질이 다릅니다. 경로별로 봤습니다.

| 경로 | 모순 | 확인 불가 |
|---|---|---|
| PRICE | 16 | 8 |
| NUMERIC | 18 | 24 |
| NARRATIVE (NLI) | 2 | 8 |
| FORECAST | 0 | 15 |

도구 경로 34건은 실제 수치와의 차이를 숫자로 제시합니다.
NLI 경로 2건은 **근거 문장이 주장과 무관했습니다.**

```
주장: 카카오 게임 사업부의 수익성 악화가 지속되었다
근거: 2019년말 카카오비즈보드 출시 이후 ... 광고매출의 수익성이 높아지고 있습니다
      -> 모순 0.999   (광고 매출 이야기로 게임 사업부 주장을 반박)
```

그래서 결과에 `confidence`(CALCULATED / INFERRED / NONE)를 붙이고
"계산 기반 커버리지"를 따로 냅니다. 둘을 한 칸에 세면 36건이지만
그중 2건은 믿을 수 없습니다.

### 대체 경로는 기본으로 끕니다 (측정으로 결정)

1차 경로가 확인 불가일 때 NLI 로 한 번 더 시도하는 경로를 만들고 재 봤습니다.

| 설정 | 모순 | 커버리지 | 속도 |
|---|---|---|---|
| 대체 경로 끔 | 36 | 39.6% | 0.54초/주장 |
| 대체 경로 켬 | 44 + 지지 1 | 49.5% | 2.51초/주장 |

커버리지가 10%p 오릅니다. 그래서 **늘어난 9건을 사람이 전수 검토했습니다.**

- 근거가 타당한 것: **1건** (셀트리온 "17.5% 상승" vs 실제 "17.4% 하락")
- 근거가 무관하거나 자의적인 것: 8건
  - 주가 변동성 주장을 부채비율·브랜드 가치로 반박
  - 매출 증감 주장을 영업이익 수치로 반박
  - 주가 수익률 주장을 "(2) 수익성지표 구분 산식 …" 표 조각으로 반박
  - 기간을 특정 못 한 주장을 임의 분기 수치로 반박
- 그중 1건은 **거짓 SUPPORTED**였습니다. 무관한 근거(부채비율 19.8%)로
  함의 0.726 이 나와 **환각을 통과시켰습니다.**

결론: 올라간 10%p 는 판정이 아니라 잡음입니다. 기본값은 끔으로 두고,
`--fallback` 으로 켜서 비교만 할 수 있게 남겼습니다.

### 작업 중 잡은 버그

**수치를 말하지 않은 주장이 모순으로 판정됐습니다.**

파서는 주장에 숫자가 없으면 값 필드를 0 으로 채웁니다. "없음"을 나타내는
필드가 따로 없기 때문입니다. 판정기가 그 0 을 그대로 비교하면 주장 구간이
`[0, 0]` 이 되어 실제 값과 절대 겹치지 않습니다.

```
주장: 셀트리온 주가는 2024년 1월 8일 ... 전장 최저점을 찍은 후 회복세를 보였다
판정: 실제 저가 204,500원 vs 주장 0원 (허용 오차 ±0원) -> 모순
```

이 주장은 그 전까지 NARRATIVE 로 분류돼 주가 도구에 들어온 적이 없었습니다.
**에이전트가 라우팅을 바꾸면서 가려져 있던 오탐이 드러났습니다.**
오탐률 0% 가 이 프로젝트의 핵심 주장이므로 바로 막았습니다.
증감률 쪽에도 같은 모양의 버그가 잠재해 있어 함께 막았습니다
(`tests/test_empty_value_guard.py` 로 고정, 4단계 지표 100%/0% 유지 확인).

**LangGraph 가 지연 로딩을 무력화합니다.**

`StateGraph.compile()` 이 노드 안에 중첩 그래프가 있는지 찾으려고
노드 함수의 바이트코드를 훑으면서 클로저가 참조하는 속성을 **실제로
`getattr` 합니다**(`find_subgraph_pregel` → `get_function_nonlocals`).
접근자를 `@property` 로 두면 그래프를 만드는 것만으로 NLI 모델과
parquet 스냅샷이 전부 올라옵니다. 전부 메서드로 바꿔서 막았습니다.

### 붙인 도구 1 — 부문별 매출 표 (`segments`)

사업보고서 '매출 및 수주상황' 절의 표를 구조화했습니다. 보고서 60건에서
수치 2,040개. 재무제표 주요계정에도 전체 재무제표에도 없는 데이터입니다.

표 파싱에서 잡은 것들입니다. 전부 **검수 장치가 먼저 잡았고**, 눈으로 몇 개
보고 넘어갔으면 그대로 틀렸을 것입니다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 기아 합계가 재무제표와 93% 차이 | 열이 기간이 아니라 **지역**(국내/북중미/유럽) | 머리글에서 기간 표기를 읽어 없으면 표를 버림 |

검수: 뽑은 수치를 재무제표 매출액과 대조. **48건 정상, 이상 0건.**
금융지주 4사(12건)는 '매출 및 수주상황' 절 자체가 없습니다.

판정에서 막은 오탐도 있습니다.

```
"2024년 1분기 POSCO홀딩스 철강 부문 영업이익은 750억원이다"
-> 공시 표에는 부문별 **매출**만 있는데 철강부문 매출 5.27조와 비교해 모순 판정
-> metric 가드 추가: 매출이 아닌 주장은 판정하지 않음
```

상한 판정도 넣었습니다. 공시에 없는 부문이라도 **전사 매출을 넘는 부문
매출은 있을 수 없습니다.** 분기 주장이면 그 분기의 전사 매출을 상한으로 씁니다.

```
"NAVER는 2024년 1분기 광고 부문에서 5조 7,839억 원의 매출을 기록했다"
-> NAVER 2024년 1분기 전사 매출 2.53조.  한 부문이 5.78조일 수 없습니다. 모순
```

### 붙인 도구 2 — 배당·지배주주순이익 (`dart_extra`)

`fnlttSinglAcntAll`(전체 재무제표)과 `alotMatter`(배당에 관한 사항)에서
주요계정 밖의 수치를 모았습니다. 284행.

**새 경로를 만들지 않았습니다.** `KNOWN_ACCOUNTS` 가 `ACCOUNT_ALIASES` 에서
자동으로 만들어지고 파서 프롬프트도 그 목록을 쓰므로, 별칭에 계정을 더하고
스냅샷에 행을 더하면 파서·판정기가 그대로 확장됩니다.

여기서도 계정명 매칭이 틀렸습니다.

```
현대차 2023 전체 재무제표에 "지배기업소유주지분" 이라는 같은 이름이 세 군데
  sj=BS   ifrs-full_EquityAttributableToOwnersOfParent      92조   (자본)
  sj=IS   ifrs-full_ProfitLossAttributableToOwnersOfParent  11.9조 (순이익)
  sj=CIS  ifrs-full_ComprehensiveIncome...                  12.2조 (포괄손익)
-> 이름으로 집으면 자본 92조를 "지배주주 순이익" 으로 기록
-> XBRL account_id 로 집도록 변경
```

### 결과

| 지표 | 3단계 | 5단계 |
|---|---|---|
| 모순 적발 | 37건 | **40건** |
| 커버리지 (전체) | 40.7% | **44.0%** |
| 커버리지 (전망 제외) | 48.7% | **52.6%** |
| 커버리지 (계산 기반) | 38.5% | **41.8%** |

새로 잡은 것들입니다.

```
현대차 2023 배당금 지급액  주장 4조 6,000억  vs  실제 2조 9,986억     -> 모순
KB금융 2024 지배주주순이익 주장 1조원        vs  실제 5조 782억      -> 모순
KB금융 2024 지배주주순이익 주장 +67%        vs  실제 +9.6%          -> 모순
NAVER 2024 1분기 광고 부문 주장 5조 7,839억 vs  전사 1분기 2.53조    -> 모순
```

### 파서 프롬프트를 바꿨으므로 4단계 지표를 다시 쟀습니다

계정 목록을 11개에서 15개로 늘리면서 프롬프트가 바뀌었습니다.
그 프롬프트는 4단계 지표(재현율 100%, 오탐률 0%)에 묶여 있어 재측정이
필요했습니다. **두 셋 모두 100% / 0% 가 그대로였고 혼동행렬에 오분류 0건**입니다.

### 작업 중 얻은 교훈

**사유 문구로 분류하면 과대 추정이 됩니다.** 3단계에서 사유 문구만 보고
"부문별 매출 9건"으로 셌는데, 부문 전용 파서로 정밀하게 읽으니 실제로
(회사·연도·부문·금액)이 모두 갖춰진 것은 **1건**이었습니다. 나머지는
연도가 없거나(3) 회사가 없거나(1) 매출이 아니었습니다(2).

부문 도구는 +1건, 배당·지배주주순이익은 +3건이었습니다. **투입 대비로는
배당 쪽이 훨씬 나았습니다.** 다음에는 사유 문구가 아니라 파싱 결과로
먼저 세야 합니다.

## 7-9. 6단계 주장 분해 품질 (2026-11-19)

5단계 분류에서 **12건이 "주장에 시점·주체가 없어서"** 판정되지 못했습니다.
원문에는 있던 정보입니다. 이 장은 그것을 고친 기록입니다.

### 먼저 기계가 셀 수 있는 기준을 만들었습니다

`scripts/check_decontextualization.py`. 사람이 눈으로 세면 고친 뒤에
좋아졌는지 알 수 없습니다. 보는 것은 셋입니다.

- 연도가 없는가
- "현재·최근" 처럼 기준일이 있어야 뜻이 정해지는 표현이 있는가
- 등락률 주장인데 시작·끝이 한쪽만 있는가

기준 자체도 두 번 고쳤습니다. 처음에는 "현재(2024년 5월 16일)" 처럼
날짜가 붙은 것까지 셌고, 그다음에는 앞쪽 날짜를 아예 안 보다가
"2024년 5월 말 현재" 를 전부 잘못 셌습니다. 조사(`부터`/`에서`)를
함께 보도록 고쳐 정확해졌습니다.

### 프롬프트 하나로 두 가지를 하려다 실패했습니다

추출 프롬프트에 "회사와 연도를 반드시 넣어라"를 더했습니다(v4, v5).

| 버전 | 주장 | NARRATIVE | 커버리지 | 시점 없음 | 주체 없음 |
|---|---|---|---|---|---|
| v3 (원래) | 91 | 38 | 83.2% | 33.0% | 7.7% |
| v4 | 79 | 30 | 74.5% | 19.0% | 0.0% |
| v5 | 74 | 24 | 71.7% | 17.6% | 2.7% |

탈맥락화는 좋아졌지만 **추출이 보수적으로 바뀌어 서술 주장을 놓쳤습니다.**
v4 가 잃은 주장 10개를 하나씩 봤더니 3개는 전망이라 빼는 것이 맞았고
5개는 잃으면 안 되는 사실이었습니다. 가장 나쁜 사례입니다.

```
원문: "2023년 연간 영업이익은 16조 원이었던 점을 고려하면,
       2024년에는 약 1.3조 원 수준의 실적이 예상됩니다."
v4:   아무 주장도 뽑지 않음
      -> 문장 전체를 전망으로 보고 버렸습니다.
         앞쪽 "2023년 영업이익 16조원" 은 확정된 사실인데도.
```

v2->v3 에서 한 번 겪은 일이 반복됐습니다. 프롬프트 하나에
"빠짐없이 뽑아라"와 "엄밀하게 다듬어라"를 같이 넣으면 둘 중 하나가 눌립니다.

### 두 단계로 나눴습니다

프롬프트는 v3 로 되돌리고, 탈맥락화를 별도 단계로 뗐습니다
(`src/pierrot/extractor/decontextualize.py`).

```
1. 분해  — 빠짐없이 뽑는 데만 집중 (prompts.py, v3)
2. 다듬기 — 회사·시점을 채우기만. 주장을 지울 수 없음
```

**안전장치를 프롬프트가 아니라 구조에 뒀습니다.** 2단계가 돌려준 개수가
입력과 다르면 결과를 통째로 버리고 원래 주장을 씁니다. "지우지 마십시오"
라고 부탁하는 대신 코드가 거부합니다. 누락은 되돌릴 수 없지만 문구는
언제든 다듬을 수 있기 때문입니다.

### "고칠 것만" 보냅니다

처음에는 주장 전부를 넘기고 "필요하면 고치라"고 했습니다.
**모델이 12개를 하나도 고치지 않고 그대로 돌려줬습니다.** 예시에 적어 둔
바로 그 문장("HBM4 개발이 성공했다")조차 그대로였습니다.

그래서 **파이썬이 먼저 판정**해, 빠진 것이 있는 주장만 **무엇이 빠졌는지와
함께** 보냅니다. 이 프로젝트가 지켜 온 방식 그대로입니다.
파이썬이 판단하고 LLM 은 쓰기만 합니다.

### 결과

| 버전 | 주장 | 커버리지 | 시점 없음 | 주체 없음 |
|---|---|---|---|---|
| v3 (1단계만) | 91 | 83.2% | 33.0% | 7.7% |
| **v7 (v3 + 다듬기)** | **94** | **83.9%** | **4.3%** | **0.0%** |

커버리지를 지키면서 탈맥락화를 잡았습니다.

```
"HBM4 개발이 성공했다"
  -> "SK하이닉스는 2024년에 HBM4 개발에 성공했다"
"POSCO홀딩스 주가는 2024년 4월 중순에 20% 이상 급등했다"
  -> "POSCO홀딩스 주가는 2024년 1월 초부터 4월 중순까지 20% 이상 급등했다"
```

에이전트 실측에서 **"1단계 주장 분해를 고쳐야 함" 12건이 0건이 됐습니다.**

| 확인 불가 원인 | 5단계 | 6단계 |
|---|---|---|
| 1단계 주장 분해 | 12건 | **0건** |
| 검증 대상이 아님 | 21건 | 27건 |
| 데이터를 더 붙이면 풀림 | 13건 | 10건 |
| 공시에 데이터가 없음 | 3건 | 8건 |
| 검색·NLI 한계 | 5건 | 8건 |

판정 수는 40 -> 41건, 커버리지는 44.0% -> 43.6%(분모가 91->94로 늘었습니다),
전망 제외 기준은 52.6% -> **53.9%** 입니다.

**판정 수가 크게 늘지 않은 것이 이 작업의 결론입니다.** 고쳐진 주장들은
"조회조차 못 함"에서 "조회했으나 공시에 그 데이터가 없음"으로 옮겨 갔습니다.

```
"SK하이닉스의 2024년 전체 HBM 매출은 45조 원 이상을 기록했다"
  5단계: "유니버스 안의 종목을 찾지 못해 근거를 모을 수 없습니다"
  6단계: "SK하이닉스 2024년 공시에 'HBM' 부문이 없습니다.
          공시된 부문: 반도체 부문 제품 외 DRAM, NAND Flash 등"
```

숫자는 비슷하지만 **진단의 질이 다릅니다.** 앞의 것은 우리 쪽 결함이고
뒤의 것은 공시의 한계입니다.

### 다듬기가 만들어 낸 오탐을 하나 잡았습니다

탈맥락화가 "전년 동기간 동안" 을 "2024년 전년 동기간 동안" 으로 바꿨고,
날짜 해석기가 이를 2023년 전체 -> 2024년 전체로 읽었습니다.

```
"LG에너지솔루션의 주가는 2024년 전년 동기간 동안 약 13% 하락했다"
-> 실제 등락률 -47.6% ~ +15.6% (63.2%p 폭)
-> 주장 -13% 가 그 안에 들어가 SUPPORTED  (오탐)
```

그만큼 넓은 구간은 **어떤 주장이든 통과시킵니다.** 정상 주장의 폭은
실측에서 2.2 ~ 12.8%p 였으므로 25%p 를 상한으로 두고 그 이상이면
판정하지 않습니다. 4단계 테스트셋에는 등락률 주장이 없어 지표에
영향이 없음을 확인했고, 두 셋 모두 100% / 0% 가 유지됐습니다.

## 7-10. 7단계 FastAPI 서빙 (2026-11-19)

지금까지 만든 것이 스크립트로만 돌아가 밖에서 쓸 수 없었습니다.
에이전트·도구·보고서를 API 하나로 묶었습니다.

### 엔드포인트

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/health` | 준비 상태. 스냅샷 5종과 키가 있는지 |
| POST | `/verify` | 답변을 분해하고 주장마다 판정 |
| POST | `/verify/claim` | 주장 문장 하나만 판정 (분해 건너뜀) |
| GET | `/usage` | 이번 달 비용을 단계별로 |

실행: `scripts/run_api.py`. 문서는 `/docs` 에서 자동 생성됩니다.

### 응답마다 운영 정보를 붙입니다

월 예산이 $5 입니다. **호출 하나가 얼마를 썼는지 응답에서 바로 보여야**
운영할 수 있습니다.

```json
"usage": {
  "elapsed_seconds": 22.227,
  "cost_usd": 0.0,
  "month_spent_usd": 0.518842,
  "month_budget_usd": 5.0,
  "llm_calls": 5
}
```

`cost_usd` 가 0 인데 `llm_calls` 가 5 인 것은 **전부 캐시 적중**이라는 뜻입니다.
0단계에서 만든 응답 캐시가 실제로 돈을 아끼고 있음이 여기서 드러납니다.

`/usage` 는 어느 단계가 돈을 쓰는지 나눠 보여 줍니다. 줄일 곳을 정하려면
이게 필요합니다.

```
numeric_parser   호출 2030  캐시 1123  $0.27426
llm_judge        호출  822  캐시  230  $0.10549
price_parser     호출 1418  캐시 1072  $0.07992
extractor        호출   85  캐시   21  $0.04473
decontextualize  호출   28  캐시    3  $0.00942
segment_parser   호출  100  캐시   60  $0.00709
```

### 검증을 직렬화했습니다

FastAPI 는 동기 엔드포인트를 스레드풀에서 돌립니다. 그런데 이 시스템이
쓰는 것들은 스레드 안전하지 않습니다.

- NLI 모델(PyTorch) 추론을 동시에 부르면 결과가 섞일 수 있습니다.
- 무엇보다 **비용을 요청별로 가를 수 없습니다.** 비용은 월 누적액의 차이로
  재는데, 두 요청이 겹치면 서로의 비용을 가져갑니다.

동시 처리보다 **얼마를 썼는지 정확히 아는 것**이 이 프로젝트에 더 중요합니다.
처리량이 필요해지면 프로세스를 늘리는 편이 낫습니다. 이 판단을 코드 주석에
남겨 두었습니다.

### 보고서 모듈을 채웠습니다 (`reporter`)

주장별 판정만 늘어놓으면 "그래서 이 답변을 믿어도 되는가"에 답하지 못합니다.
1단계에서 기록해 둔 원문 구간(span)을 써서 **원본 답변 위에 표시**합니다.

```
삼성전자는 2024년 3분기에 6조 1,879억 원의 영업이익을 기록하며
시장 예상치를 상회했습니다. [모순] 매출은 68조 423억 원이었습니다. [모순]
```

표시는 **뒤에서부터** 끼워 넣습니다. 앞에서부터 하면 뒤쪽 구간의 위치가
밀려 엉뚱한 자리에 붙습니다.

요약에는 판정의 성격을 나눠 담습니다(`calculated` / `inferred`).
둘을 한 칸에 세면 "모순 3건"이 되지만 그중 1건은 NLI 추정이라 믿을 수
없습니다. 보고서를 읽는 사람이 그 차이를 알아야 합니다.

### 연기 테스트에서 오탐을 하나 더 잡았습니다

실제 답변을 API 에 넣어 보니 SUPPORTED 가 하나 나왔는데, 오탐이었습니다.

```
"삼성전자 주가는 2024년 3분기 실적 발표 직후 71,800원까지 하락했다"
-> "3분기" 로 해석되어 92일 구간, 저가 61,500 ~ 88,800원 (44% 폭)
-> 주장 71,800원이 그 안에 들어가 SUPPORTED
```

6단계에서 등락률에 넣은 것과 **같은 종류의 구멍**이 값 주장에도 있었습니다.
4단계 어려운 셋의 값 주장은 폭이 최대 23.6% 였으므로 35% 를 상한으로
두었습니다. 두 셋 모두 100% / 0% 유지를 재측정으로 확인했습니다.

고친 뒤 사유가 이렇게 바뀝니다.

```
"기간이 너무 넓어 저가를 특정할 수 없습니다.
 2024-07-01 ~ 2024-09-30 (92일) 동안 61,500원 ~ 88,800원(44% 폭)라,
 그 사이 어떤 값이든 들어맞습니다."
```

**연기 테스트를 돌리지 않았으면 못 찾았을 오탐입니다.** 테스트셋은 데이터가
있는 조건으로 만들어져 이런 모호한 표현이 들어 있지 않습니다.

## 8. 검토했던 다른 후보 (참고용)

- **삐에로 마스크**: 금융 문서 개인정보 비식별화 파이프라인. 외부 LLM 전송 전 자동 마스킹, 응답 후 복원. 금융권 규제 대응에 강점.
- **삐에로 지표 에이전트**: 뉴스 감성과 주가 흐름의 괴리를 탐지하고, 멀티 에이전트가 원인 분석 리포트를 작성. 증권사 지원에 강점.

PIERROT를 선택한 이유: 환각 검증은 금융, 제조, 일반 AX 등 어느 도메인에도 필요한 주제이므로,
금융 데이터로 시연하면서도 "검증 도구만 바꾸면 다른 도메인에 적용 가능하다"는 범용성을 설명할 수 있습니다.
