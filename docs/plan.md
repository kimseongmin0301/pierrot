# PIERROT 설계 문서

> 이 문서는 Cowork 대화(2026-11-18)에서 정리한 내용을 Claude Code에서 이어서 작업하기 위해 옮긴 것입니다.

---

## 1. 배경: 왜 이 주제인가

### 1-1. 목표 직무

AI / AX 엔지니어. 이 직무에서 주로 보는 역량은 세 가지입니다.

1. **LLM을 실제 업무 흐름에 붙이는 능력**: RAG, 에이전트, 도구 호출(Tool Calling)
2. **AI 결과를 믿을 수 있게 만드는 능력**: 평가(Evaluation), 가드레일, 환각 탐지
3. **운영 능력**: 로그, 모니터링, 비용과 지연시간 관리

RAG 챗봇과 에이전트는 이미 구축 경험이 있으므로, 이 프로젝트는 **2번(신뢰성)**을 차별점으로 보여주는 데 집중합니다.

### 1-2. 삐에로라는 주제와의 연결

삐에로(Pierrot)는 이탈리아 즉흥극(코메디아 델라르테)에서 유래한 캐릭터로,
**웃는 분장 뒤에 슬픔을 숨긴 광대**라는 상징을 가집니다.

LLM도 틀린 답을 할 때 자신 있게 웃는 얼굴로 말합니다. 이것이 "LLM의 가면"입니다.
PIERROT는 이 가면을 벗겨서 답변의 실제 근거 여부를 드러내는 시스템입니다.

또한 "신뢰를 중요하게 여기고, 결과를 의심하고 직접 검증한다"는 개발자 본인의 강점이
프로젝트 주제와 일치하므로, 면접에서 일관된 이야기로 연결할 수 있습니다.

## 2. 동작 흐름 (금융 도메인 예시)

```
사용자 질문: "삼성전자 3분기 영업이익과 주가 흐름 요약해줘"
        ↓
[1] 답변 생성 LLM
    - 일반적인 RAG 방식으로 답변 생성
        ↓
[2] 주장 분해 (Claim Extraction)
    - 답변을 검증 가능한 최소 문장 단위로 분리
    - 예: "3분기 영업이익은 X조원이다"
          "발표 후 주가가 5% 상승했다"
        ↓
[3] 검증 에이전트
    - 주장의 유형을 분류하고, 유형에 맞는 도구를 선택해 확인
    - 숫자 주장  → DART 공시 API 조회
    - 주가 주장  → OHLCV 데이터 조회 후 직접 계산
    - 서술 주장  → 원문 문서와 의미 비교 (NLI 모델)
        ↓
[4] 판정
    - 주장별로 세 가지 중 하나로 판정
      · SUPPORTED     : 근거 있음
      · CONTRADICTED  : 근거와 모순
      · UNVERIFIABLE  : 근거를 찾을 수 없음
        ↓
[5] 최종 출력
    - 원래 답변에 주장별 신뢰 표시를 붙임
    - CONTRADICTED 주장은 근거와 함께 수정 제안
```

## 4. 기술 구성

| 영역 | 기술 | 면접에서 어필되는 점 |
|---|---|---|
| 답변 생성 | Ollama(`gemma3:4b`) + RAG | 오픈 모델 로컬 서빙 경험 |
| 에이전트 | LangChain + LangGraph | 도구 선택, 분기, 재시도 설계 |
| 검증 도구 | DART API, FinanceDataReader 스냅샷, 한국어 NLI 모델 | 외부 시스템 연동 |
| 평가 | 직접 만든 정답셋 + 2단 베이스라인 비교 | AI 품질을 숫자로 증명 |
| 서빙 | FastAPI (Python), 필요 시 Spring Boot 게이트웨이 | 서비스화 능력 |
| 운영 | 응답 캐시, 토큰·비용 로거, LangSmith 트레이싱 | LLMOps 감각 |

구체적인 모델 선정과 근거는 **7장**에 있습니다.

## 5. 평가 설계 (이 프로젝트의 핵심)

포트폴리오가 "만들어 봤다"로 끝나지 않으려면 **검증기 자체를 검증해야** 합니다.

1. **테스트셋 구축**
   - 정상 답변을 기반으로, 일부러 틀린 정보를 섞은 답변 200~300개를 만듭니다.
   - 오류 주입 방식: 숫자 바꾸기, 날짜 바꾸기, 인과관계 뒤집기, 근거 없는 주장 추가
   - 각 주장에 정답 라벨(SUPPORTED / CONTRADICTED / UNVERIFIABLE)을 붙입니다.

2. **측정 지표**
   - 재현율(Recall): 틀린 주장을 얼마나 잡아내는가
   - 오탐률(False Positive Rate): 맞는 주장을 틀렸다고 잘못 판정하는 비율
   - 정밀도(Precision): CONTRADICTED로 판정한 것 중 실제로 틀린 비율

3. **비교 실험** (상세 근거는 7-4)
   - 베이스라인 ①: 한국어 NLI 모델 단독 검증
   - 베이스라인 ②: LLM-as-judge — `gpt-4o-mini`에게 근거와 주장을 주고 직접 판정시킴
   - 개선안: 도구 기반 검증(DART, 주가 계산) 추가
   - 결과 예시 형식: "도구 기반 검증 추가 후 재현율 +N%p, 오탐률 -M%p"

4. **테스트셋의 한계를 명시합니다**
   - 오류 주입으로 만든 테스트셋은 정답 라벨이 정확한 대신, 실제 LLM이 내는 환각과
     분포가 다릅니다. 이 한계를 숨기지 않고 README에 명시합니다.
   - 가능하면 `generator`(`gemma3:4b`)가 실제로 만들어 낸 환각 샘플을 소수라도 수집해
     보조 검증 세트로 함께 사용합니다.

## 7. 확정된 결정 사항 (2026-11-18)

### 7-1. LLM 구성

| 자리 | 모델 | 실행 위치 | 비용 |
|---|---|---|---|
| `generator` (검증 대상 답변 생성) | `gemma3:4b` | ai-server (Ollama) | $0 |
| `generator` 비교 실험 (선택) | `qwen3:4b` | ai-server (Ollama) | $0 |
| RAG 임베딩 | `embeddinggemma` | ai-server (Ollama) | $0 |
| `extractor` (주장 분해) | `gpt-4o-mini` | OpenAI API | 유료 |
| `verifier` (검증 판단) | `gpt-4o-mini` | OpenAI API | 유료 |
| 베이스라인 ① NLI | `Huffon/klue-roberta-base-nli` | 로컬 CPU | $0 |
| 베이스라인 ② LLM-as-judge | `gpt-4o-mini` | OpenAI API | 유료 |

**선정 근거**

- `generator`는 검증 **대상**이므로 품질이 좋을 필요가 없고, 오히려 환각이 섞여야 시연이 자연스럽습니다.
  4B급 로컬 모델이 이 역할에 적합하며, "사내 로컬 LLM의 답변을 검증한다"는 서사는 외부 API 반출이
  어려운 금융권 환경과 그대로 맞아떨어집니다.
- `extractor` / `verifier`는 시스템의 **부품**이므로 품질이 중요합니다. `gpt-4o-mini`는 추론 모델이
  아니라 비용 예측이 정확하고, Structured Outputs(JSON 스키마 강제)를 지원해 파싱이 안정적이며,
  LangChain 자료가 가장 많습니다.
- 1단계 완료 기준(샘플 10개 사람 검토)에서 주장 분해 품질이 부족하면 그때 `gpt-5-mini`로 올립니다.

**예산: 월 $5**

| 항목 | 평가 1회 비용 |
|---|---|
| `generator` (로컬) | $0 |
| `extractor` | 약 $0.14 |
| `verifier` | 약 $0.50 |
| 베이스라인 ① NLI (로컬) | $0 |
| 베이스라인 ② LLM-as-judge | 약 $0.32 |
| **합계** | **약 $0.95** |

Batch API(50% 할인) 적용 시 약 $0.48. 월 $5로 전체 평가를 5~10회 실행 가능합니다.

**예산을 지키기 위한 필수 장치 (0단계에 포함)**

1. **디스크 응답 캐시** — 프롬프트 해시를 키로 응답을 저장. 재실행 시 변경된 부분만 과금됩니다.
   비용 절감과 동시에 평가 재현성을 확보하는 장치이기도 합니다.
2. **토큰·비용 로거** — 모든 호출의 입출력 토큰과 환산 비용을 기록합니다.
   원래 6단계 항목이었으나 **0단계로 앞당깁니다.** 예산이 $5면 사용량을 모르는 채로 개발할 수 없습니다.
3. **개발 중 미니 테스트셋** — 평소 개발은 10~20개 샘플로, 전체 300개는 로직 확정 후에만 실행합니다.

### 7-2. 에이전트 구현 방식 — LangChain + LangGraph

| 도구 | 담당 |
|---|---|
| LangChain | LLM 호출, 프롬프트 템플릿, 출력 파싱, SQLite 응답 캐시(`set_llm_cache`) |
| LangGraph | `verifier`의 상태 머신: 유형 분류 → 도구 선택 → 호출 → 실패 시 재시도 → 판정 |
| LangSmith | 요청별 트레이싱(선택, 무료 티어). 토큰·지연시간 기록을 자동화 |

**경계선**: `evaluation` 모듈은 LangChain에 의존시키지 않습니다. 지표 계산(정밀도/재현율/오탐률)은
순수 파이썬으로 유지합니다. 프레임워크 버전 변경으로 과거 평가 결과를 재현하지 못하는 상황을
막기 위해서입니다. 이 프로젝트의 핵심 주장이 "숫자로 증명했다"인 이상, 그 숫자를 만드는 코드는
외부 의존성이 가장 적어야 합니다.

### 7-3. 주가 데이터 소스 — FinanceDataReader

**원칙: 평가 실행 중에는 외부에서 주가를 조회하지 않습니다.**

```
[1회성 수집 스크립트]  →  로컬 스냅샷(parquet)  →  [검증 도구가 조회]
  FinanceDataReader 사용        저장소에 커밋          외부 접속 없음
```

pykrx, FinanceDataReader 등은 공식 API가 아니라 거래소·포털을 크롤링하는 비공식 라이브러리입니다.
대상 사이트 구조가 바뀌면 동작이 멈추고, 수정주가 반영 시점에 따라 값이 달라질 수 있습니다.
외부 의존성을 재현성 경계 밖으로 밀어내기 위해 스냅샷 방식을 사용합니다.

- 수집 범위(확정): 고정 유니버스 20종목, **2023-01-02 ~ 2026-11-18**
  (18,920행, 494KB, `data/snapshots/kospi_ohlcv.parquet`)
- **종목 유니버스를 코드에 고정합니다** (`src/pierrot/tools/universe.py`).
  "시가총액 상위 20종목"처럼 동적으로 정하면 돌리는 시점마다 구성이 바뀌어 평가를
  재현할 수 없습니다. 유니버스는 실험 조건의 일부이므로 고정하고 커밋으로 흔적을 남깁니다.
  구성은 1단계 샘플에 등장한 10개 기업 + 코스피 대형주 10개입니다.
  (참고: `fdr.StockListing('KOSPI')`의 시가총액 필드가 `NaN`이라 동적 선정이 불가능하기도 합니다.)
- 종목명↔종목코드 매핑은 유니버스에 별칭까지 적어 두고 직접 찾습니다.
  "현대자동차"나 "포스코홀딩스" 같은 표기도 이어져야 하기 때문입니다.
- 등락률은 LLM에게 묻지 않고 **파이썬으로 직접 계산**합니다. 이것이 도구 기반 검증의 핵심입니다.

#### 발견된 한계: 수정주가 (2026-11-18)

스냅샷을 받아 보니 20종목 중 3종목의 과거 시세가 **수정주가로 보정**되어 있었습니다.
분할·합병·인적분할이 있으면 과거 가격이 소급 조정되기 때문입니다.

| 종목 | 호가 단위에 맞는 종가 비율 |
|---|---|
| 삼성바이오로직스 | 3.6% |
| 셀트리온 | 12.8% |
| 삼성SDI | 41.6% |
| 나머지 17종목 | 99.9 ~ 100% |

**왜 문제인가**: LLM이 "2024년 7월 26일 주가는 85만원이었다"고 말할 때 그 값은
당시 호가를 가리킵니다. 보정된 시세(1,336,279원)와 비교하면 맞는 주장을 틀렸다고
판정하게 됩니다. 오탐은 이 프로젝트가 가장 피해야 할 오류입니다.

**반대로 등락률 주장에는 수정주가가 맞습니다.** 분할 전후를 비교 가능하게 만드는
것이 수정주가의 목적이기 때문입니다.

**대응**: 보정 여부를 호가 단위 검사로 **자동 탐지**하고(목록을 코드에 적지 않습니다.
스냅샷을 다시 받으면 대상이 달라지는데 하드코딩하면 조용히 틀린 채로 남습니다),
보정된 종목의 "얼마였다" 주장만 UNVERIFIABLE 로 둡니다. 등락률 주장은 그대로 판정합니다.

**대안 검토**: pykrx 의 `adjusted=False` 로 원주가를 받으려 했으나 KRX 로그인이
필요해 실패했고, `adjusted=True` 값은 FinanceDataReader 와 동일했습니다.
무료로 비수정 주가를 안정적으로 얻을 방법은 찾지 못했습니다.

### 2단계 착수 순서를 바꾼 이유 (NLI 먼저 → 주가 먼저)

계획 초안은 NLI를 먼저 만드는 것이었으나, 실제로는 NLI가 가장 복잡합니다.
혼자서는 아무것도 못 하기 때문입니다.

| 도구 | 근거를 어디서 가져오나 |
|---|---|
| 주가 | 스스로 해결. 로컬 스냅샷에서 조회 |
| DART | 스스로 해결. API가 수치를 직접 반환 |
| NLI | **해결 못 함.** 비교할 근거 문서가 어디에도 없음 |

`generator`는 환각을 유도하려고 RAG 없이 답변을 만들었으므로 참고 문서가 존재하지 않습니다.
NLI부터 만들면 "무엇과 비교할 것인가"가 공중에 뜬 채로 도구를 만들게 됩니다.
반면 DART 도구를 만들면 거기서 받아 오는 **공시 원문이 곧 NLI의 근거 문서**가 되므로,
주가 → DART → NLI 순서로 가면 각 단계가 다음 단계의 입력을 만들어 줍니다.

### 7-4. NLI 모델과 베이스라인 구성

**베이스라인을 2단으로 둡니다.**

| 단계 | 방식 | 역할 |
|---|---|---|
| 베이스라인 ① | `Huffon/klue-roberta-base-nli` | 전통적 방식. 숫자에 약하다는 것을 실측으로 보여주는 자리 |
| 베이스라인 ② | LLM-as-judge (`gpt-4o-mini`) | "요즘은 LLM에 직접 물어보면 되지 않나"라는 가장 현실적인 반론 |
| 개선안 | 도구 기반 검증 (DART, 주가 계산) | 이 프로젝트의 주장 |

베이스라인이 하나뿐이면 "NLI 모델을 약한 걸 골라 놓고 이긴 것 아닌가"라는 반론을 막을 수 없습니다.
②가 있어야 **"NLI보다 나은 건 당연하고, LLM에게 직접 물어보는 방식보다도 낫다"**는 결론이 가능합니다.

**NLI의 구조적 한계가 이 프로젝트의 핵심 논거입니다.**

- 근거: "3분기 영업이익은 9조 1,800억원입니다."
- 주장: "3분기 영업이익은 10조원입니다."

NLI 모델은 문장 구조가 거의 같으므로 entailment(함의)로 판정하는 경우가 흔합니다. 의미의 흐름을
보도록 학습됐을 뿐 숫자를 값으로 계산하지 않기 때문입니다. 이를 실측으로 드러내는 것이
DART 조회·주가 계산이라는 도구가 필요한 이유가 됩니다.

**구현 주의사항**

- RoBERTa 계열 NLI는 입력 512 토큰 제한이 있습니다. 근거 문서가 길면 문장 단위로 분할해 각각
  판정하고 최대 entailment 점수를 취합니다.
- `base`급(파라미터 약 1.1억)이라 CPU 추론으로 충분합니다. ai-server의 VRAM이 4GB뿐이고
  `gemma3:4b`가 대부분을 사용하므로, NLI는 **로컬 PC의 CPU**에서 실행합니다.
